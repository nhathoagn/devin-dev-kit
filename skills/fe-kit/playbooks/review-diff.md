# Review a diff

Use this when the task is to review a diff, or before a non-trivial code edit is called done — any source file, not only frontend. The author of the diff does not fill this report.

You are not the author. You do not have the writing session. Do not praise. Do not edit, commit, checkout, or spawn another reviewer.

## Fan-out (the author runs this part)

One reviewer grades one diff once. To reach most issues in one pass, the author fans out reviewers by lens, merges the reports, fixes once, then verifies once — and, when the fix creates a new contract surface (a new guard, validator, `Result` type, or signature), runs a second lens pass on the new version. A pass only grades the version it was run on; a finding on version 1 cannot be checked on version 2 without a fresh pass.

- A diff of 10 files or fewer: run `python3 ../../scripts/review_lenses.py list` from this skill folder and spawn one reviewer per lens, in parallel. Each task adds `--lens <name>` and names its diff range.
- A larger diff: run `review_packages.py split`, spawn one reviewer per package for the whole checklist, plus one extra reviewer with `--lens contract` over the whole range (callers, spec, and tests cross package borders).
- When the task names `--lens <name>`, the reviewer walks only that lens's items (step 3). It still reports anything else it sees, and its report carries a `Lens: <name>` line.
- Merge all reports with `review_packages.py merge --out <file> <reports>`. One spot (`file:line`) seen by two lenses becomes one paragraph that names every lens that saw it.
- Fix every finding of `nên sửa trước` and `nên sửa trong lượt này` in one pass, run the gate commands, then spawn one fresh reviewer whose task is the merged findings list and the new diff. A finding still true at HEAD goes back to the fix pass, once. A second open finding means the fix approach is wrong, not the review.
- A fix that adds a guard, validator, `Result` type, or new signature also gets a second lens pass on the new version: spawn `--lens correctness` and `--lens contract` plus `--lens probe` and `--lens invariant` from `review_lenses.py list`. The probe lens applies `{undefined, null, "", " ", NaN, -1, 0}` at every boundary; the invariant lens checks each A→B call pair for a promise narrower than the dependency (the `orderProblem` pattern). Loop ends when a pass on the same version produces zero `nên sửa` findings — not after a fixed number of passes.


1. Get the diff. If the task names `BASE` and `HEAD`, use `git diff --stat BASE..HEAD` and `git diff BASE..HEAD`, and note the commits with `git log --oneline BASE..HEAD`. If the task names only `BASE` (`--diff <sha>` with no `..`), use `git diff BASE`. Otherwise use `git diff HEAD`. With no `HEAD` in the range, also read each untracked file: the project rules command below prints every file to review on a `file:` line, new files included. Read a file only to judge a hunk.
   Then run the project rules command for the same range: the `Project rules command:` line of the task or the hook, or `python3 ../../scripts/project_config.py --root <repo> --mode review` from this skill folder. Add the task's `--diff` (`BASE..HEAD`, or `BASE` alone) when it names one. Add `--files` of the package when the task gives one; `--files` with `--diff` reads that package of the range. Read each `read:` line it prints. Do not review a file under `skip:`. Step 2 uses its `spec_dirs:`. The `.fe-kit/config.yaml` file is optional: with no config, the command searches `AGENTS.md`, `CLAUDE.md`, and `rules/` folders. Exit 2 is a broken config: say that in one line under Kết luận and review with the checklist alone.
2. Find the spec file. Stop at the first hit. Do not fetch an issue tracker. Do not run `setup-matt-pocock-skills`. Do not open `code-review`. Do not spawn a reviewer. Search three sources in order: (a) a path or an issue reference (`#45`, `Closes #45`, `Fixes #45`, a bare `#45`) in the subject or body of a commit inside the range, (b) a spec path the task names, (c) a file whose whole stem equals the branch name or the feature the diff adds. A hit is a file under a folder of `spec_dirs:` from step 1 (`docs/`, `specs/`, `.scratch/` when the repo sets none) that exists at HEAD with that exact spelling: a missing path, another case, a root or `src/` file, and a directory are not hits — a file path given beside such a directory still counts. An issue number must be a whole token in the file name: `45-address.md`, `checkout-45.md`, and `issue-45-address.md` match `#45`; `145-address.md`, `450-address.md`, `4.ts`, and `5.ts` do not. When source (a) hits, do not read (b) or (c) even when a later file disagrees. A branch hit needs the stem equal to the whole branch name; the part after a slash never matches. Read only the hit file. When the hit exists but is empty, or holds only a heading, it gives no requirement: stop there — do not fall to another source, do not take a task requirement, and do not build one from the code. When no source hits, say that in one line under Kết luận; a file that merely exists in the repo is not a hit. Then judge the stated task, or the checklist alone when the task states none.
3. Read `references/REVIEW_CHECKLIST.md` and `references/review-checks.md`. Walk every item — or only the items of `--lens <name>` when the task names one; `python3 ../../scripts/review_lenses.py items <name>` prints them, and everything else still gets reported when it is wrong. F20 uses the file from step 2. F21 reads `GLOSSARY.md` or `CONTEXT.md` at the repo root when one exists. If only `GLOSSARY-MAP.md` exists, read the one file it names for this feature. Do not create a glossary. Do not write an ADR. Do not apply the Architecture smell list in `references/audit.md`. Do not print a code, `PASS`, `FAIL`, or `N/A`. If the diff adds or changes a check (`?? ''`, `startsWith`, `trim`, `min`, `safeParse`, or a filter/map over fields), apply `undefined`, `null`, `""`, `" ABC"`, and `"ABC "` to that check before the verdict. A value that produces no error is a finding, with `file:line`. Do not write "Đưa được" if you did not apply them. The same five values go through every guard the diff adds or changes over a parameter (`if (!discount)`, `x || …`, `x ?? …`): a value that returns through with no error is a finding like any other. When all five values produce an error, the check satisfies that requirement: write no finding against it, and do not demand an enforcement the spec does not name (a disabled button, a submit guard).

The judgement list in `references/audit.md` is not scored here. Do not write a paragraph from it in any framing — not as a smell, and not as runtime safety: fields travelling together, replacing a string or number with an existing type, a repeated switch or if, a chain like `a.b().c()`, a forward-only component, inheritance that drops props, or a brand-new file that holds two jobs of its own. The checklist has no item for them on a diff.
4. Apply each project rule file from step 1 to the files it was printed for. A filled row under "Lỗi riêng của repo" in a root `REVIEW_CHECKLIST.md` is one such rule. Skip an empty rule cell. Where a project rule and this checklist disagree on a name, a layer, or a pattern, the project rule wins. A finding from a project rule quotes that rule as `path:line`.
   When the task lists findings of an earlier review, open each one at its `file:line` at HEAD. A finding that still holds goes in the report again, as a finding of this review. A fixed finding is not reported.
   When the task gives `--files` of one package, review only those files.
5. Search the callers. When the diff changes the signature, the return value, or the behavior of an exported function, hook, component prop, or type, search every caller in the repo, also outside the diff. A caller that the diff breaks is a finding at the caller's `file:line` (C8, D7).
6. Ignore a hit a linter already catches, unless a repo row says otherwise. Ignore a problem outside the diff, unless the diff makes it worse.
7. Check each finding again before you write it. Open its line again: does that line do what the finding says? Name what the user loses. When you cannot name it, drop the finding. Two findings with one root cause are one paragraph. This step drops a wrong finding. It never drops a true finding to shorten the report.
8. Write the report by filling `references/review-output.md`. Follow Cách viết in that file. The reader sees those sentences, not checklist codes. Do not add a Spec section.
9. Check the report. Write it to a temp file with Bash, then run `python3 ../../scripts/review_check.py --root <repo> --report <file>` from this skill folder, with the same `--diff BASE..HEAD` or `--files` as step 1. Exit 1: fix the report and run it again. Do not change the script. A `!` line needs a check by hand. A reference outside the diff must be a caller from step 5: keep it, or remove it. A line in a file the diff deleted: confirm it with `git show BASE:<path>`. Then print the report and stop.

## Verdict words

Say the verdict in the first sentence, in Vietnamese.

- A defect that loses data, ships a secret, or breaks the build: "nên sửa trước". The first sentence is "Không đưa lên".
- A defect the user will hit in this screen: "nên sửa trong lượt này". If none are "nên sửa trước", the first sentence is "Sửa rồi hãy đưa".
- A nit: "có thể để sau". If nothing else failed, the first sentence is "Đưa được".

## Report

The report is `references/review-output.md`, filled. Do not add a checklist section. Do not add a Spec section.

The task gives the gate result: each `gate:` command and its exit code, run by the author before the hand-off. Write it under Cổng. Do not run the gate yourself, because parallel reviewers can share one test database. When the task gives no result, write `Cổng: chưa chạy (task không gửi kết quả)`.
