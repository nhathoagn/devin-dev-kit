# Clean up non-UI code

Use this when the task is to clean up, shorten, or restructure code that is not a component, screen, hook, or form — services, domain logic, adapters, scripts, test helpers — and no behavior should change. UI restructuring goes to `playbooks/refactor-ui.md`; wrong behavior goes to `playbooks/fix-bug.md`; a rewrite whose diff goes through lens review follows `playbooks/author-loop.md` after this playbook's edit batch.

1. Read `references/ownership.md`. Record the five ownership fields. A wrong placement in scope goes to the sweep table; the cleanup moves it, or lists it under Không đụng tới with a reason.
2. Read `references/reuse.md` and `rules/reuse-duplication.md`. Record the reuse decision. Duplication the cleanup merges names the surviving owner and every caller migrated.
3. Do not read `references/performance.md` unless the code in scope does I/O, loops over unbounded data, allocates on a hot path, or the task is about speed or memory. Otherwise write `n/a` and say why.
4. Read `references/code-quality.md`. Fill the sweep table. Rows a non-UI file cannot hold get `n/a` with a reason: `Form screens` when scope has no form, `Design and behavior` when the task is not a legacy port. A port of an old system follows `presets/legacy-rewrite/` and those rows run for real. Follow the fix rule in Sweep: fix what the task asks and what this turn writes; list the rest.
5. Read `references/audit.md`. Fill the Audit table for the code the cleanup touches. A cleanup that leaves two paths for one rule is not done.
6. Do not read `references/feature-isolation.md`. A cleanup adds no behavior, so nothing gets a flag. Write `n/a` and say why. If the task also adds behavior, that behavior goes through the playbook for its kind — it is not part of this cleanup.
7. Read `references/smells-checklist.md`, `references/fowler-checklist.md`, `references/posd-checklist.md`, then `references/tidy-checklist.md`. The first names smells on the code the cleanup will touch — run it before the first edit so the plan knows what it is removing. The second scores the code it touched: extracted methods, changed signatures, split modules. The third asks what the first two do not: is each touched module deep, does a new interface push complexity up to its callers, could an error case be defined away. The fourth governs how the work lands: tidying moves for code too tangled to touch safely and tidy commits kept separate from any behavior the task also adds.
8. Read `references/external.md`. For a match, read the installed skill file, or fetch it per that file. If none match, write `n/a` under Departures / Notes and name the skip.

Verify without a screen. A cleanup does not change output, so run the project's type-check, lint, and every test covering the touched module. When the module has no tests, write a throwaway harness that calls each exported function you changed on representative inputs, snapshot the outputs before the first edit, re-run after the last, compare byte for byte, then delete the harness. A difference blocks "done" until you explain it or revert. Report each command and its exit code.

Edit gate: declare `Runtime owner:` and `Decision:` before the first edit of a source file the gate covers, as `rules/fe-implementation.md` says — not only `.tsx`; the gate also covers `.ts`, `.jsx`, `.js`, `.mjs`, `.cjs`, `.vue`, `.svelte`, `.astro`, `.mdx`, and the other source languages.
